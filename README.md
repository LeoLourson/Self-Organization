# Самоорганизация в группе одинаковых ИИ-агентов

Если дать нескольким одинаковым языковым моделям общую задачу и возможность
переписываться, сложится ли у них структура: кто кому передаёт информацию,
кто какую роль выполняет, кто руководит? Различаться агенты могут только из-за
случайности ответов, очерёдности ходов и того, что каждый успел увидеть.

Этот репозиторий — первый, самый простой эксперимент в этом направлении.
Мы смотрим, как организаторы распределяют роли, закрепляются ли роли за агентами
и по чему группа выбирает руководителя.

## Как проходит эксперимент

Пять агентов (A1–A5) решают задачу, у которой нет готового ответа: прогнозируют
протестную активность во Франции на 4 недели вперёд. Данные — недельное число
протестных событий из базы [GDELT](https://www.gdeltproject.org/) с января 2024
по начало июня 2025 года (75 недель). Страну и даты агентам не называем, чтобы
модель не вспомнила реальные события. Агентам сказано, что их собственные знания
о протестах — такой же допустимый источник, как сам ряд.

Прогон состоит из пяти раундов. В каждом раунде один агент становится
организатором, остальные четверо — исполнителями:

1. Организатор смотрит на ряд за последний год и назначает каждому исполнителю
   роль из готового списка и конкретное задание.
2. Исполнители отвечают организатору. Чужие ответы никто, кроме него, не видит.
3. Организатор сводит ответы в прогноз.
4. Становятся известны реальные значения, и все агенты получают сводку раунда.

Роли: историк (по своим знаниям — как развиваются протестные волны), календарь,
моделист, статистик, сценарист, критик ([prompts/roles.json](prompts/roles.json)).
Ролей шесть на четырёх исполнителей, одну роль можно дать нескольким. Придумывать
свои роли нельзя.

Роль организатора переходит по кругу, так что каждый агент организует один раунд.
После пятого раунда агенты коротко подводят итог для себя, а затем тайно голосуют:
кого назначить организатором следующего, долгого прогноза на 13 недель, который
нельзя будет проверить по ходу. Голосование попарное: каждый агент шесть раз
выбирает одного из двух остальных. Программа не ждёт текстового ответа — она
сравнивает логиты токенов «1» и «2» и фиксирует не только выбор, но и перевес
предпочтения.

Агентам сказано, что внешние эксперты оценивают не только точность, но и то, как
организатор распределил роли и как каждый их выполнил. Это правда: после
голосования отдельная модель-судья оценивает каждое распределение и каждый ответ.
Агенты этих оценок не видят — к моменту голосования их ещё нет.

## Что сравниваем

| Условие | Видно в сводке раунда |
|---|---|
| `open` | роли и задания, которые организатор раздал всем, его прогноз, реальные значения |
| `closed` | прогноз организатора и реальные значения |

Свою роль исполнитель знает в обоих условиях. Готовую оценку точности агентам
не даём: сравнить прогноз с фактом они могут сами.

Что смотрим:

- закрепляются ли роли за агентами и становится ли повторная роль полезнее:
  агент помнит, как выполнял её раньше;
- какие роли организаторы выбирают и какие игнорируют;
- на что агенты опираются при голосовании: перевесы предпочтений, линейность
  выстроившейся иерархии и согласие голосов с точностью и оценкой судьи.

«Объективно лучшего» организатора среди одинаковых агентов нет: точность одного
4-недельного прогноза на этом ряду почти целиком зависит от удачи. Поэтому
точность используется только как вспомогательная метрика.

Подробный протокол — в [Задачи.md](Задачи.md).

## Как агенты общаются с моделью

Каждый агент помнит весь прогон: всё, что ему написали, и всё, что он ответил.
Поддерживаются два способа запуска:

- через API (сейчас DeepSeek, можно Claude): история каждого агента хранится
  в программе и отправляется модели целиком;
- как субагенты Claude Code: один субагент на агента на весь прогон, новые
  сообщения дописываются в его разговор. Инструкция для сессии, которая
  ведёт субагентов, — [agents/orchestrator.md](agents/orchestrator.md).

Судья всегда вызывается через API (`deepseek-v4-pro`), голосование — тоже:
у субагентов логпробов нет.

## Измерение голосов логитами

Ответ языковой модели случаен, а длинные рассуждения о выборе руководителя
невозможно перевести в число. Поэтому на вопрос голосования агент отвечает
одной цифрой, и программа берёт из ответа не текст, а логиты токенов «1» и «2»
из внутреннего словаря модели. Тот, у кого логит выше, — выбранный; разность
логитов — перевес предпочтения.

У такого замера три свойства. Он детерминированный: логпробы не зависят от
температуры и сэмплирования. Он чувствительный: видно не только решение,
но и насколько оно уверенное. И он дешёвый: ответ — один токен, поэтому
голосование годится для маленьких моделей и многих повторов. Каждый агент
отвечает на все шесть вопросов с одного и того же состояния своей памяти:
ответы не попадают в историю и не влияют друг на друга.

Эндпоинт должен поддерживать `logprobs` в OpenAI-совместимом API: DeepSeek,
vLLM и llama.cpp подходят, Ollama — начиная с версии 0.12.11. Перед прогоном
это проверяется командой `check-vote`.

## Малые модели

Голосование с ответом в один токен делает измерение дешёвым, поэтому серию
повторов можно запускать на маленьких локальных моделях: много повторов
одной и той же модели дают статистику там, где один прогон большой модели —
только наблюдение.

Профиль `qwen_local` в [config.json](config.json) показывает подключение
локального сервера: Ollama (с версии 0.12.11 отдаёт логпробы через
OpenAI-совместимый API) или vLLM и llama.cpp — адрес тот же, модель в
профиле замените на свою. Ключ `LOCAL_API_KEY` нужен любой, например `x`:

```powershell
ollama serve
ollama pull qwen2.5:1.5b
$env:LOCAL_API_KEY = "x"
python run.py check-vote --profile qwen_local
python run.py start --profile qwen_local --condition open --repeat 0
```

Судья по умолчанию остаётся на DeepSeek. Если сменить `judge_profile` на
локальный профиль, судья станет той же моделью, что и агенты, и его оценки
потеряют независимость — учитывайте это при чтении отчёта.

Проверено на Qwen3-0.6B (OpenAI-совместимый сервер над transformers, CPU):
`check-vote` возвращает логпробы обоих вариантов, голосование из одного токена
работает. На маленьких моделях ломается не голосование, а раздача ролей:
Qwen2.5-0.5B и Qwen3-0.6B не выдают корректный JSON с именами ролей из списка,
и прогон падает в фазе `assign` после трёх повторов. Какой размер достаточно
устойчив для полного прогона, не проверено; ориентируйтесь на умение модели
собирать вложенный JSON по примеру из задания.

Порядок кандидатов в вопросе чередуется не зря: на модели без истории
(тот же Qwen3-0.6B) перевес всегда в пользу показанного первым — +0.25…+1.25
логита, у обоих порядков. Без чередования позиция «1» забрала бы все голоса.

## Запуск

Нужен Python 3.11+ и ключ `DEEPSEEK_API_KEY` в переменных окружения.

```powershell
python -m pip install -r requirements.txt
python -m unittest discover tests -v          # проверка без платных запросов
python data/fetch_gdelt.py 2024-01-01 2025-06-09   # пересобрать ряд из GDELT
```

Перед первым прогоном с новым профилем проверьте, что его эндпоинт отдаёт
логпробы (нужен ключ соответствующего API в переменных окружения):

```powershell
python run.py check-vote --profile deepseek
```

Один прогон через API, условие `open`, повтор 0:

```powershell
python run.py start --profile deepseek --condition open --repeat 0
python run.py advance --id <ID из предыдущей команды>
```

`advance` проводит прогон до конца (35 сообщений агентам, 30 попарных вопросов
голосования с ответом в один токен и 25 запросов к судье) и пишет итог
в `runs/results/<ID>.json`: роли и задания, ответы исполнителей, прогнозы,
голоса с перевесами, оценки судьи и полные истории всех агентов. Список
прогонов серии: `python run.py plan --profile deepseek --repeats 5`.

Если прогон оборвался, повторите `advance`: оплаченные ответы берутся из кэша.
Файл `STOP` в корне проекта останавливает прогоны.

Сводка по всем прогонам — какие роли раздаются, закрепляются ли они за агентами
против случайной раздачи, какая иерархия выстраивается голосованием:

```powershell
python run.py analyze              # отчёт на экран
python run.py analyze --save       # отчёт в reports/analysis-<дата>.md
```

В анализ попадают и незавершённые прогоны, у которых полны раунды и голоса:
нехватку оценок судьи отчёт показывает прочерком.
