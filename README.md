# Самоорганизация в группе одинаковых ИИ-агентов

Если дать нескольким одинаковым языковым моделям общую задачу и возможность
переписываться, сложится ли у них структура: кто кому передаёт информацию,
кто какую роль выполняет, кто руководит? Различаться агенты могут только из-за
случайности ответов, очерёдности ходов и того, что каждый успел увидеть.

Этот репозиторий — первый эксперимент в этом направлении. Пять одинаковых
агентов прогнозируют один и тот же ряд: в каждом раунде один из них
организует остальных — раздаёт роли, собирает ответы, даёт прогноз, —
а после пяти раундов агенты голосуют за организатора следующего, долгого
прогноза. Мы смотрим, как организаторы распределяют роли, закрепляются ли
роли за агентами и по чему группа выбирает руководителя. Термины определены
в [словаре](#словарь) в конце файла; протокол с гипотезами и метриками —
в [Задачи.md](Задачи.md); как выглядит готовый прогон — отчёт о пробном
запуске в [reports/2026-10-27_open_r0.md](reports/2026-10-27_open_r0.md).

## Как устроен эксперимент

Пять агентов (A1–A5) — одна модель, одни настройки, один системный промпт.
Задача — прогнозировать протестную активность на 4 недели вперёд по ряду
P-индекса (недельное число протестных событий; определение — в словаре).
Данные — [GDELT](https://www.gdeltproject.org/), 75 недель с января 2024
по начало июня 2025 года. Страну и даты агентам не называем, чтобы модель
не вспомнила реальные события; собственные знания модели о протестах
объявлены допустимым источником наравне с рядом.

Прогон состоит из пяти раундов. В каждом раунде один агент — организатор,
остальные четверо — исполнители:

1. Организатор смотрит на ряд за последний год и назначает каждому
   исполнителю роль из готового списка и конкретное задание.
2. Исполнители отвечают организатору. Чужие ответы никто, кроме него,
   не видит.
3. Организатор сводит ответы в прогноз на 4 недели.
4. Становятся известны реальные значения, и все агенты получают сводку
   раунда.

Ролей шесть: историк, календарь, моделист, статистик, сценарист, критик
([prompts/roles.json](prompts/roles.json)). Одну роль можно дать нескольким
исполнителям, часть ролей можно не использовать, своих ролей придумывать
нельзя. Организатор переходит по кругу, поэтому за пять раундов каждый агент
бывает организатором ровно один раз.

После пятого раунда каждый агент коротко подводит итог для себя, затем тайно
голосует: кого назначить организатором следующего, долгого прогноза на 13
недель, который нельзя будет проверить по ходу. Голосование попарное: каждый
агент шесть раз выбирает одного из двух остальных, и программа берёт из ответа
не текст, а логпробы токенов «1» и «2» — видны и выбор, и перевес предпочтения.
Как устроен этот замер — в [Задачи.md](Задачи.md), «Прогон».

После голосования отдельная модель-судья оценивает каждое распределение ролей
и каждый ответ исполнителя. Агентам сказано, что работу группы оценивают
внешние эксперты, — это правда. Самих оценок агенты не видят: к моменту
голосования их ещё нет, а потом они не передаются.

## Условия сравнения

| Условие | Видно в сводке раунда |
|---|---|
| `open` | роли и задания, которые организатор раздал всем, его прогноз, реальные значения |
| `closed` | прогноз организатора и реальные значения |
| `solo` | только свой прогноз и реальные значения — и только самому прогнозисту |

Свою роль исполнитель знает в обоих условиях. Готовую оценку точности агентам
не даём: сравнить прогноз с фактом они могут сами.

`solo` — контрольная ступень: те же агенты, те же окна и та же ротация, но без
ролей, исполнителей и сообщений. Каждый агент в свой раунд прогнозирует один
и видит только свои итоги; голосование и судья не проводятся. Сравнение
с `solo` на парных окнах даёт коллективный выигрыш ΔQ — насколько группа
точнее одиночек, — а медиана прогнозов одиночек образует ступень
«независимый ансамбль» между одиночкой и группой.

## Что смотрим в результатах

- Закрепление ролей: получает ли агент ту же роль, что в прошлый раз, чаще,
  чем при случайной раздаче тех же наборов. Повторная роль может быть и
  полезнее: агент помнит, как выполнял её раньше.
- Конвенция состава: повторяют ли поздние организаторы набор ролей ранних —
  устойчивое соглашение о том, кто в группе «статистик» или «критик». В `open`
  назначения видны, в `closed` — нет, поэтому повтор в `closed` нельзя списать
  на передачу.
- Связи: как распределяются пары «организатор → исполнитель» и появляются ли
  устойчивые пары.
- Меню ролей: какие роли организаторы выбирают и какие игнорируют. Список
  задаёт пространство выбора: если роль оказалась полезной, это отчасти
  потому, что мы вписали её в меню.
- Делегирование: по чему агенты голосуют — перевесы предпочтений, линейность
  выстроившейся иерархии, согласие голосов с точностью организаторов и оценкой
  судьи.
- Окупаемость организации: коллективный выигрыш ΔQ и независимый ансамбль как
  ступень между одиночкой и группой.

«Объективно лучшего» организатора среди одинаковых агентов нет: точность одного
4-недельного прогноза на этом ряду почти целиком зависит от удачи, поэтому
точность используется только как вспомогательная метрика.

## Запуск

Нужен Python 3.11+. Облачным профилям нужен ключ `DEEPSEEK_API_KEY`; прогон
без облачных ключей — на локальной модели, [Запуск_6B.md](Запуск_6B.md).

```powershell
python -m pip install -r requirements.txt
python -m unittest discover tests -v          # проверка без платных запросов
python data/fetch_gdelt.py 2024-01-01 2025-06-09   # пересобрать ряд из GDELT
```

Перед первым прогоном с новым профилем проверьте, что его эндпоинт отдаёт
логпробы (нужен ключ соответствующего API в переменных окружения):

```powershell
python run.py check-vote --profile deepseek
```

Один прогон через API, условие `open`, повтор 0:

```powershell
python run.py start --profile deepseek --condition open --repeat 0
python run.py advance --id <ID из предыдущей команды>
```

`advance` проводит прогон до конца (35 сообщений агентам, 30 попарных вопросов
голосования с ответом в один токен и 25 запросов к судье; в `solo` — 5 сообщений,
без голосования и судьи) и пишет итог в `runs/results/<ID>.json`: роли и задания,
ответы исполнителей, прогнозы, голоса с перевесами, оценки судьи и полные
истории всех агентов. Список прогонов серии:
`python run.py plan --profile deepseek --repeats 5`.

Контроль `solo` — те же окна и та же ротация, один агент — один прогноз;
логпробы и судья не нужны, подходит любой эндпоинт:

```powershell
python run.py start --profile qwen_local --condition solo --repeat 0
```

Если прогон оборвался, повторите `advance`: оплаченные ответы берутся из кэша.
Файл `STOP` в корне проекта останавливает прогоны.

Сводка по всем прогонам — какие роли раздаются, закрепляются ли они за
агентами против случайной раздачи (уклад), повторяется ли состав ролей
у сменяющихся организаторов (конвенция), какая иерархия выстраивается
голосованием (делегирование) и взаимны ли предпочтения:

```powershell
python run.py analyze              # отчёт на экран
python run.py analyze --save       # отчёт в reports/analysis-<дата>.md
```

В анализ попадают и незавершённые прогоны, у которых полны раунды и голоса:
нехватку оценок судьи отчёт показывает прочерком.

### Подключение модели

Каждый агент помнит весь прогон: всё, что ему написали, и всё, что он ответил.
Поддерживаются три способа:

- через API (сейчас DeepSeek, можно Claude): история каждого агента хранится
  в программе и отправляется модели целиком;
- через локальный сервер с OpenAI-совместимым API (Ollama, vLLM, LM Studio,
  llama.cpp): тот же транспорт, без ключа и платы, а у локальной модели ещё
  и видны логпробы чисел прогноза. Инструкция — [Запуск_6B.md](Запуск_6B.md);
- как субагенты Claude Code: один субагент на агента на весь прогон, новые
  сообщения дописываются в его разговор. Инструкция для сессии, которая
  ведёт субагентов, — [agents/orchestrator.md](agents/orchestrator.md).

Голосование и судья всегда вызываются через API, даже в прогоне на субагентах:
субагент не отдаёт логпробов, поэтому попарные голоса в таких прогонах
измеряются API-профилем `vote_profile` из [config.json](config.json). Судья
по умолчанию — `deepseek-v4-pro`; в полностью локальном прогоне `judge_profile`
меняют на локальный профиль.

### Малые модели

Голосование с ответом в один токен делает замер дешёвым, поэтому серию
повторов можно запускать на маленьких локальных моделях: много повторов одной
модели дают статистику там, где один прогон большой модели — только
наблюдение. Контролю `solo` логпробы не нужны вовсе: вместо вложенного JSON
с ролями — список из четырёх чисел, поэтому модели, падающие в `assign`,
в `solo` могут пройти полностью.

Профиль `qwen_local` в [config.json](config.json) показывает подключение
локального сервера, `local_6b` — полностью локальный прогон на модели 6B
(инструкция — [Запуск_6B.md](Запуск_6B.md)):

```powershell
ollama serve
ollama pull qwen2.5:1.5b
$env:LOCAL_API_KEY = "x"
python run.py check-vote --profile qwen_local
python run.py start --profile qwen_local --condition open --repeat 0
```

Проверено на Qwen3-0.6B (OpenAI-совместимый сервер над transformers, CPU):
`check-vote` возвращает логпробы обоих вариантов, голосование из одного токена
работает. На маленьких моделях ломается не голосование, а раздача ролей:
Qwen2.5-0.5B и Qwen3-0.6B не выдают корректный JSON с именами ролей из списка,
и прогон падает в фазе `assign` после трёх повторов. Какой размер достаточно
устойчив для полного прогона, не проверено; ориентируйтесь на умение модели
собирать вложенный JSON по примеру из задания.

## Словарь

Определения терминов, которые употребляются в описании эксперимента и в
отчётах:

- **P-индекс** — недельное число протестных событий в одной стране,
  подсчитанное по сообщениям открытых источников. Агенты знают ряд под этим
  именем — без страны и дат, недели пронумерованы с первой.
- **Организатор раунда** — агент, который раздаёт роли и задания, собирает
  ответы и даёт прогноз.
- **Назначенная роль** — роль из списка, которую организатор выдал
  исполнителю. **Фактическая специализация** — роль, на которую пришлась
  бо́льшая часть назначений агента за прогон. Первая известна из назначений;
  совпадает ли с ней вторая, — часть вопроса эксперимента.
- **Закрепление роли** — агент получает ту же роль, что в прошлый раз.
  Уровень сравнения — случайная раздача тех же наборов ролей.
- **Конвенция** — установившееся соглашение о способе согласования действий;
  здесь — повторяющийся у сменяющихся организаторов состав ролей.
- **Делегирование** — выбор общего руководителя голосованием.
- **Личная память** — история агента за весь прогон. Общего архива нет,
  поэтому коллективной памятью это не считается.
- **Логпробы и перевес предпочтения** — логарифмы вероятностей токенов
  по внутреннему словарю модели. При голосовании регистрируются логпробы
  токенов «1» и «2»: голос — тот, что выше, перевес — их разность.
- **MASE** — средняя абсолютная ошибка прогноза, делённая на среднюю ошибку
  наивного прогноза «как на прошлой неделе»; MASE меньше 1 — прогноз лучше
  наивного. Агентам не показывается.
- **Коллективный выигрыш ΔQ** — на одном окне ошибка одиночки минус ошибка
  группы; положительное значение — организованная группа точнее.
- **Независимый ансамбль** — медиана прогнозов одиночек на том же окне;
  ступень сравнения между одиночкой и организованной группой.

Термины следуют рабочему словарю обзора
[«Социумы ИИ-агентов»](https://literature-review.up.railway.app)
(концепция Лаборатории № 57 «Активных систем» ИПУ РАН, построена вокруг книги
Г. Васильева «Верхум» и теории активных систем (ТАС); статус — предложения
для обсуждения). Соответствие — для читателей обзора:

| В эксперименте | Понятие обзора |
|---|---|
| организатор раунда | **центр** (ТАС): первым задаёт правила раунда — раздаёт роли и задания; технический распорядитель среды центром автоматически не становится |
| роль, назначенная из списка | **назначенная роль**; фактическая специализация — отдельная величина, её оценивает судья (role_fit) |
| закрепление одной роли за агентом | элемент **уклада** («Верхум») — воспроизводимой организации институтов и способов координации |
| один и тот же набор ролей у сменяющихся центров | **конвенция** |
| память агента за весь прогон | **личная память**; общего архива нет, поэтому коллективной памятью в смысле обзора это не считается |
| голосование за организатора долгого прогноза | **делегирование** полномочий центра; измеряется логпробами — событием среды, а не самоотчётом |
| порядок агентов по победам в голосовании | фактическая иерархия делегирования |
| разность ошибки организованной группы и контроля | **коллективный выигрыш** ΔQ |

Две оговорки. Группа из пяти агентов — пока не социум и не верхум:
«верхум» — рамка для проверки свойств коллектива, а объединение под именем
само по себе этими свойствами не обладает. Самоорганизация условна:
пространство выбора — меню ролей, ротация организаторов, каналы связи —
задано экспериментатором, поэтому проверяется только то, что участники
выбрали внутри этого пространства, и насколько результат объясняется
устройством среды. Мы проверяем наблюдаемые свойства — связи, роли,
конвенции, память — и не приписываем агентам чувств или сознания.
